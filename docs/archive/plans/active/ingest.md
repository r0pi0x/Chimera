# Plan: asset ingestion (original media to signed packs anyone can rebuild)

Status: proposed 2026-11-15. This is a plan only: nothing in it is
built yet. It answers the user's requirements of 2026-11-15, recorded
in the backlog's "Generated asset sets on the asset service" (its
"Reproducible by anyone" part), with "The sandbox, and progressive
downloads" and "Ladder draw" as neighbours
([backlog](../../backlog.md), roadmap). Section 9 lists the questions
for the user.

Words used here:

- An **original** is the media a game ships: a Steam install at a build,
  or a disc image. An **original record** is one of its files as the
  game reads it. Combat Arms' archive entries and TF2's `.ctx` scripts
  count as decrypted.
- A **record** is a file in the store, named by the SHA-256 of its plain
  bytes. A **manifest** maps paths to records and names **sets**
  (`chimera/assets/src/manifest.rs`).
- A **unit** is what a player downloads atomically: one gun, one TF2
  class, one Halo character, one map. It is a set, plus the units it
  needs.
- A **recipe** is a game's ingestion described as data. A **converter**
  is versioned code that turns original records into **generated
  records**.
- **Authored** content is our own work (the logo's characters, arena
  slices), which the repository may hold. **Custom** content is a third
  party's own work, built into a **custom pack**.
- A **content id** is what a manifest is for: an official game
  (`combat_arms`), `chimera` (authored), or a custom pack's namespace.

## 1. Goals and non-goals

Goals:

1. **One pipeline beside the asset service.** `chimera_pack ingest <game>
   --from <original media> --store <dir>` identifies and validates the
   original, mounts it, discovers its content, runs the converters,
   derives every set from declared dependencies, signs, and writes a
   report. The resulting store drops into any asset service
   (`chimera_asset_server` serves it as it serves today's stores).
2. **Reproducible by anyone.** Another host with the same original and
   the same Chimera version gets the same manifest content (section
   3.10): the same records, the same sets, the same generated bytes.
   Recipes, converters and their documentation ship in this
   repository.
3. **Generated records only from documented, versioned, deterministic
   converters.** Each generated record carries its recipe: converter,
   version and input hashes. A format change regenerates or runs a
   documented migration. Nothing is ever hand-made.
4. **New official content needs no code change.** A newer original (a
   Combat Arms patch with new guns, maps or bodies) is picked up by
   re-ingesting, because recipes discover content from the game's own
   catalogues. Our model of each item (its weapon document, its parts
   claim, its tags) is derived from the game's data, with safe defaults
   and a report of what couldn't be mapped. Hand-tuned overrides are
   optional data layered on top.
5. **Custom content by third parties**: weapons first, then maps, player
   models and HUD content. It is namespaced, built by the same pipeline
   from the author's own files, signed by its author, trusted per server,
   and holds data and assets only.
6. **Fits what exists and what's designed:** per-unit atomic downloads,
   `request_set`/`SetProgress`, service-first clients, server credentials,
   the sandbox's tags and filters, and the ladder draw.

Non-goals:

- **No original files, extracted files or keys in the repository**
  (CLAUDE.md, hard rules). Recipes name files and hashes, which are facts
  about files; they never hold contents. Reference manifest ids, as in
  `assets.lock`, are facts too.
- **No conversion on a player's machine for the service.** Clients with
  an install keep converting locally, as today (the converted-map cache,
  `chimera/assets/src/map_cache.rs`). The pipeline runs on a host.
- **No code in custom content, ever** (section 5.4).
- **No cross-game balance** in derived numbers. A derived weapon keeps
  its game's own values.
- **No change to the wire format or to what shipped clients read until a
  phase says so.** The manifest's format 1 stays readable (section 3.8).

## 3. Architecture

### 3.1 The command

```
chimera_pack ingest <game> --from <original> --store <dir>
    [--recipe <file>]        a recipe other than the game's own (games/<id>/ingest.toml)
    [--accept-unknown]       ingest an original whose build or fingerprint the recipe doesn't know
    [--only <set prefix>]    derive only some units (as `sets --only`)
    [--check-runs <log>...]  completeness check against CHIMERA_VFS_LOG runs or the service's access log
    [--sign]                 sign with the store's server key (a server store)
    [--dry-run]              identify, discover and report; write nothing
chimera_pack ingest custom --from <author's folder> --store <dir> --author-key <file>
chimera_pack regenerate <content id> --store <dir> [--converter <name>]   generated records again, from the originals in the store
chimera_pack verify <content id> --store <dir> --against <manifest content id>   rebuild check (3.10)
```

The command is a `chimera_pack` subcommand (open question 1). It shares
the store, packing and signing code. The pipeline itself is a library
crate, `chimera/ingest` (`chimera_ingest`), which holds the recipe
format, discovery and walker registries, the converter interface, set
derivation, the sidecar and the report. It names no game. Each game
crate implements its walkers, discoverers and converters behind an
`ingest` feature, which pulls the pipeline into tools only. The binary
at the root links the games, as `chimera_pack` does today. `pack`,
`sets`, `lean` and `publish` stay for one release as thin wrappers
around the pipeline, then go (7).

Keys come from the environment only: `CHIMERA_<GAME>_KEY_<NAME>`, plus
the local config for the game apps. TF2's `CHIMERA_TF2_CTX_KEY` already
has this form. Combat Arms gains `CHIMERA_COMBAT_ARMS_KEY_V1` and `_V2`
(key and IV). Keys are never written to a manifest, a sidecar, a report
or a log. A report says only "supplied" or "absent".

### 3.2 Recipes

A recipe is a TOML file per game at `games/<id>/ingest.toml`. It is our
own data: names, hashes and rules, never contents. It says:

- **What original it accepts:** its kind (`steam_install` with an app,
  `disc_image`, `folder`), the known builds, and the identity files whose
  hashes fingerprint a build. The fingerprint finds a modified or
  partial install, and identifies a disc whose build string isn't
  enough.
- **How to open it:** the game's mount by name (`open_install`,
  registered by the game), the extra layers and their sets, the folders
  left out, the keys and whether each is required, and the layers that
  aren't original media (3.3).
- **What to discover** (3.4): the catalogues, by named discoverer.
- **What to produce:** the units per catalogue with their set names, the
  shared sets with their declarers, and the converters with their
  parameters.
- **Its own version** (`version`): bumped when the recipe's output could
  change.

Code supplies the format knowledge: discoverers, walkers and converters,
registered by name as weapon hooks are. The recipe chooses and wires
them. A sketch for Combat Arms (names illustrative):

```toml
recipe = "combat_arms"
version = 1

[original]
kind = "steam_install"
app = 1263550
builds = ["<build id>"]                  # known builds; others need --accept-unknown
identity = ["Game/ATTRIBUTES.rez", "Game/WORLDS.rez"]   # hashed into the fingerprint
mount = "combat_arms"                    # combat_arms::game::mount::open_install
keys = [{ name = "V1", env = "CHIMERA_COMBAT_ARMS_KEY_V1", required = true }]
layers = [{ name = "loose_music", set = "music" }]
scope = "whole"                          # pack every file; "declared": only what the sets name

[[discover]]
what = "weapons"
by = "combat_arms:attribute_weapons"     # the install's weapon records, merged as data.rs merges them
unit = "weapon/{id}"
also = ["parts/{id}"]                    # a gun with parts gets its fitted-parts unit

[[discover]]
what = "characters"
by = "combat_arms:body_records"
unit = "character/{record}"

[[discover]]
what = "maps"
by = "combat_arms:worlds"
unit = "map/{name}"

[shared]
base = ["combat_arms:startup_files"]     # what every start reads: attribute files, menus, fonts
common = ["combat_arms:effect_tables", "combat_arms:voices", "combat_arms:debris", "combat_arms:strike"]
players = ["combat_arms:stock_bodies"]
"music/{track}" = ["combat_arms:bgm_tracks"]

[[convert]]
converter = "chimera:catalogue"          # 3.6
[[convert]]
converter = "chimera:map_fitness"
```

Halo's recipe differs only in data: `kind = "disc_image"`, its known
disc fingerprints, `build` read by `halo_ce::game::mount::build`
(`01.10.12.2276`), `left_out = ["xdemos/"]`, a donor map, and later a
`halo_ce:character_unit` converter per campaign character (3.6). TF2's
names `scope = "declared"`, since a whole publish is 31 GB at level 19,
and an optional `ctx` key.

### 3.3 Identifying and validating the original

1. **The build**: from the Steam app manifest (`install::install_build_id`)
   or the game's own reader (Halo's maps' header string).
2. **The fingerprint**: SHA-256 over the recipe's identity files' hashes,
   in a fixed order. For a disc image, the image's own hash or its
   `default.xbe` and maps' hashes. An original whose build or fingerprint
   the recipe doesn't know is refused unless `--accept-unknown` is given.
   It is then ingested as "unverified" in the sidecar and the report, so
   it can't claim to match a reference (3.10).
3. **Keys**: each required key is present and opens the identity files.
   A wrong key fails here with the archive named, not halfway through.
4. **Non-original layers**: CS:S's mount shows its `download/` folder and
   Chimera's content cache, which hold the publisher's community maps.
   These are not original media. The recipe marks such layers
   `community`. Their maps are ingested into the game's manifest with the
   kind `community` in the sidecar (open question 3), and never count
   toward the reproducibility check. Another host's pack has different
   community maps.
5. **Completeness of the original**: every path any unit's walk asks for
   is either in the original or listed in the report as a reference to a
   missing file (the game's own data naming absent files is common, and
   the report keeps it visible).

### 3.4 Discovery, and our model derived from the game's data

A **discoverer** reads a game's own catalogue from the mounted original.
It returns items with stable ids and the data each derivation needs.

| Game | Weapons from | Characters from | Maps from |
|---|---|---|---|
| Combat Arms | the attribute file's weapon records (`data::attributes`) | `MODELBUTES` body records | the world files (`world::map_names`) |
| TF2 | `scripts/items/items_game.txt` stock items, with their `.ctx` scripts | the class table (fixed) | `maps/*.bsp` |
| CS:S, HL2:DM | the recipe's fixed roster (the committed documents) | the recipe's fixed roster | `maps/*.bsp` |
| Halo | the fixed roster now. Later the multiplayer `weap` tags | the donor's Spartan. Later the campaign's bipeds (specs/halo_ce/characters.md) | the disc's multiplayer maps |

Each item then gets **our model**, derived in three layers. The later
layer wins:

1. **Derived**: the game's data mapped field by field, as
   `combat_arms::game::data::weapon_values` and its siblings do today.
2. **Template**: what the data can't say is taken from the nearest
   committed document, picked by the game's own classification. Combat
   Arms uses `Guntype` with the projectile record, as in `template_for`.
   TF2 uses `item_class`. A weapon's behaviour beyond numbers lives in
   the hooks its template names.
3. **Overlay**: hand data in `games/<id>/data/overrides/` (today's
   `display_names.toml`, `ladder_exclusions.toml` and `map_pool.toml`
   already work this way), keyed by id or glob. An overlay is never
   required. A missing one leaves the derived value.

**Safe defaults**: an item with no template (a new `Guntype` or
`item_class`) still gets a unit with its files and a weapon document from
the generic base of its delivery kind (hitscan, projectile, melee or
thrown). That document has `class` unset, so automatic ladders don't
deal it until someone looks: an overlay assigns a class or a template.
The report lists every such item and every field that wasn't mapped,
with the default used.

**Tags** (for the sandbox's filters) are derived in one place,
`chimera_sim::weapon` (a `tags(&WeaponData) -> Vec<Tag>` function), from
the final document:

- the game and the content id, official or custom;
- the class (`GunClass`) and slot;
- the delivery (hitscan, projectile, melee, thrown, flame);
- the trigger (automatic, semi, burst, charge, spin);
- whether it reloads by magazine or shell by shell;
- whether it has parts or a zoom;
- the power band (`minigame::power`).

Overlays may add or remove tags. Tags are written into the catalogue
record (3.6), so the sandbox filters with nothing downloaded.

Characters, maps and HUD content follow the same three layers. A
character's movement, hit boxes and hands come from its record (Combat
Arms' figure types, Halo's biped tags) or its game's defaults. A map's
pool membership comes from the deny and allow rules plus its measured
fitness. HUD content is the game's own HUD, keyed by game; only custom
HUD content (5.7) is new.

**`GameParts` as data**: `parts::PARTS` stays the Rust claim for what
needs code (movement and HUD ids are code). Its `guns` list, already
supplemented by every catalogue weapon with a `class`, shrinks to
nothing over time. A data `parts.toml` per content id carries the rest
(announcer, cues, match sounds, maps first in a pool), so a custom pack
can register parts with no code (5.6).

### 3.5 Units and set derivation

For each discovered item the recipe names a unit (`weapon/{id}`). A
**walker** lists the unit's files:

- **Loader-traced walkers (phase I2)**: today's `record_pieces` bodies,
  moved into each game crate as `ingest::walk_weapon`, `walk_body`,
  `walk_map` and so on. Each loads the piece through the game's own
  loaders on a tracked mount (`Tap`, `Mount::track`). This is
  deterministic and needs no match or play. Files only checked for
  (`held`, `contains`) are listed apart and never put in a set.
- **Format walkers (later, where they pay)**: references read straight
  from the formats (an MDL's materials, a VMT's textures, a sound
  script's waves) for units where loading is slow or needs a world.
  Both kinds give the same answer, and a test compares them.

Then, as `chimera_pack sets` does today, but declared:

1. **Shared sets** come from the game's declarers: `base` (what every
   start reads), `players` and `common` (what every match of the game
   reads), and `music/<track>`. A declarer is a function of the game's
   data, never of a run. Today's `base` additions inside `record_pieces`
   (cue packs, match-end sounds, guest looks, effect tables, debris,
   default hands, the air strike) become declarers one for one.
2. **Unit sets** have the shared sets subtracted, as map sets already
   leave out `base`, `players` and `common`. A unit that becomes empty
   keeps its files (Halo's donor-map rule).
3. **Needs**: a unit lists the units it needs. A TF2 class needs the
   classes in `classes.toml`'s `needs` (every class, for the Spy once
   disguise exists). A Combat Arms gun's `parts/<id>` needs its
   `weapon/<id>`. A custom gun needs the official unit it builds on. A
   Halo character needs `base`. The closure is what `request_set` and
   the offer fetch.
4. **Determinism**: sets are sorted path lists, and walkers run in a
   fixed order, so the manifest's bytes don't depend on threads.

**Completeness check** (`--check-runs`): play-run reads stop being a
source. Given `CHIMERA_VFS_LOG` logs, or the asset service's access log
(its ` on-demand` lines, playtest-hosting.md "Files fetched mid-match"),
the report lists:

- every file a run read that no set holds (a missing declaration);
- with the run's match named, every file read outside the closure of
  the sets the offer would name (a mid-match fetch waiting to happen).

The run's log gains a header line naming its map and ladder (a
`chimera_assets::recording` change). Each finding is fixed by adding a
declaration, never by recording.

### 3.5a The asset graph (user, 2026-11-15)

The user asked that assets form a dependency graph with a hierarchy, so that packs simply refer into it. That replaces the flat sets-plus-`needs` model of 3.5 as the way to think about content. Sets stay as the wire format underneath.

- **Records** are the leaves. Every file is stored once by content hash, as today, so a texture shared by twenty guns costs nothing extra.
- **Units** are the nodes: the smallest thing anything asks for. Each has a hierarchical id, `<namespace>/<kind>/<id>`:
  - `tf2/weapon/tf_weapon_minigun`, `tf2/body/heavy`, `halo_ce/character/grunt`, `halo_ce/voice/grunt`;
  - `cs_source/map/de_dust2`, `combat_arms/hud`;
  - a custom pack's `<author>.<pack>/weapon/<id>`.

  The kind is typed (base, map, weapon, body, character, voice, hud, music, generated). A unit owns a list of records.
- **Edges**, typed:
  - `requires`: must be present before the unit is used; fetched with it.
  - `deferred`: wanted, but fetched after the unit is usable, in the background (Halo's voices after the body; a map's ambient music).
  - `optional`: used if present, never fetched for it (a game's own icon over the kit's).
  - `variant-of`: a reskin or custom gun built on an official unit, reusing its records.
- **Hierarchy:** a namespace's units nest by kind, and a game's `base`, `common` and `players` become ordinary units that others `require`. The sandbox's games, classes and guns tree, and the ingest report, read straight off it.
- **Packs** are named, versioned roots: a list of unit ids plus a namespace's trust and signature. Examples: "Ultimate Gun Game's official content", "TF2 base", a custom weapon pack. A pack never copies a unit; it refers to it. The same goes for a ladder, a map pool or a match offer: each is a set of roots, and the client and server fetch the graph's closure. `requires` comes now, `deferred` later, and `optional` never.
- **Validation at ingest:** no cycles; every edge resolves within trusted namespaces; a custom unit may point into official units but never the reverse; the report prints each unit's own and closure sizes.
- **On the wire:** the graph is written in the signed side file beside the manifest (3.8). Old clients keep reading the flat sets, which ingest still emits as the closure of each root. New clients resolve the graph themselves. TF2's `classes.toml` `needs`, Halo's characters and voices, and Combat Arms' parts become graph edges declared by the recipes.
- **Fetching:** `request_set` from the sandbox becomes `request_unit`. `SetProgress` reports per unit and for the closure. The no-fetch-in-match guard allows only `deferred` edges in a match, within a bandwidth budget. Built 2026-11-16 on today's sets (`chimera_net::net::units`: `request_unit`, `UnitProgress`, the guard; `deferred` is a kind prefix, `voice/`, until the graph's edges exist, and `requires` is the game's shared sets plus `UnitNeeds` hooks).

### 3.6 Converters

A converter has a name (`<namespace>:<name>`: `chimera:catalogue`,
`chimera:map_fitness`, `halo_ce:character_unit`), a version, and a
documented output format. Sketch:

```rust
trait Converter {
    const NAME: &str;
    const VERSION: u32;            // bumped by hand when any output byte could change
    fn inputs(&self, params: &Params, catalog: &Inputs) -> Vec<String>;   // the paths it will read
    fn convert(&self, params: &Params, read: &dyn Fn(&str) -> Option<Vec<u8>>) -> Result<Vec<(String, Vec<u8>)>, String>;
}
```

The rules (each enforced by a test):

- **Inputs are declared and enforced.** `read` serves only the declared
  paths, as the store's records. A read outside them fails the
  conversion, so the recorded input hashes are exactly what was used.
- **Pure.** No clock, environment, file system, network, randomness or
  thread-dependent order. Outputs are sorted (`BTreeMap`, never
  `HashMap` order). Floats are formatted with a fixed method. Output
  never depends on the platform's `libm` (transcendental functions
  differ between Linux and Windows): converters use integer or
  pure-Rust math. The thread count doesn't change output.
- **Byte-identical**: the same inputs, params and version always give
  the same bytes. Compression happens after hashing, so the zstd
  version or level never matters.
- **Version discipline**: each converter has golden hashes of its
  output on synthetic fixtures that its tests write (no game files).
  Changing the output without bumping `VERSION` fails the test with
  "bump the version". The golden hashes are checked on Linux and
  Windows.
- **Paths**: generated records live under `chimera/gen/<converter>/v<version>/...`
  in the content's manifest. No original path is ever replaced, and two
  versions can be served side by side while clients update.
- **Incremental**: a converter's output is keyed by (name, version,
  params hash, input ids). A re-ingest that finds the key already in
  the store skips the work.
- **Documented**: docs/generated-assets.md (new in phase I4) has a
  section per converter with its inputs, outputs, format, versions and
  what each version changed.

**Versions and the engine**: a client knows which converter versions it
reads (a `READS` range per converter, in the crate that consumes the
output). When the engine changes a generated format:

- **Regenerate** (the steady state): `chimera_pack regenerate` runs the
  new version from the original records, which the store already holds.
  Decrypted records included, so no keys and no media are needed.
- **Migrate** (when the originals aren't at hand, for instance on a
  service that received only generated sets): a registered, versioned
  step `migrate <converter> v<n> -> v<n+1>` that reads old generated
  records only. It is documented and tested like a converter, and its
  outputs record the migration in their recipe.

Never a format nobody can rebuild.

First converters, in order of use:

| Converter | Output | Why |
|---|---|---|
| `chimera:catalogue` | per content id, one small record: each unit's id, full and short name, class, tags, set name, needs, plain and stored size, and icon path | the sandbox's rows with nothing downloaded: names, classes, tags and "not downloaded (size)" (backlog, sandbox). Its inputs are the game's data files. Combat Arms' merge runs here, with its version covering `data.rs`' derivation |
| `chimera:map_fitness` | per map, today's `map_fitness.toml` entry (walkable area, sight, spawns, spots) | a new official map is measured at ingest and joins pools by its numbers with no commit. The committed file becomes an overlay for maps the measurement can't judge |
| `halo_ce:character_unit` | per campaign character, a self-contained unit cut from the campaign map: its biped, animation graph, model, hit boxes, shields, dialogue and the tags those reference | halo-ce.md's decision: each character fetched as its own unit, never a whole campaign map. Its format (a minimal cache file our Halo loader reads unchanged, or our own) is open question 11 |
| `chimera:icons` (later) | per gun, a small icon at fixed sizes | the sandbox's rows and kill feeds without a model download |
| `chimera:map_converted` (later, if measured worth it) | the converted map as `map_cache` stores it | a client without CPU to convert. Needs its encoding proved deterministic first: its chunked, threaded writer must give fixed bytes |

### 3.7 Signing

As today, the service's key signs each manifest's exact bytes, and it
signs the sidecar too (`<build>.ingest.sig`). An ingest run with
`--sign` signs with the store's key (`server::key_path`). Without it,
`chimera_pack sign` signs later on the server, as for a store packed
elsewhere. Custom packs add the author's signature (5.3).

### 3.8 Manifest and provenance

`Manifest::parse` refuses unknown keys, so new lines in format 1 would
break every shipped client. Provenance therefore goes in a **sidecar**,
`manifests/<content>/<build>.ingest`. It is plain text, sorted and
signed. Old clients never fetch it, and new clients fetch it with the
manifest:

```text
chimera-ingest 1
content combat_arms
build <build>
original steam_install app=1263550 fingerprint=<sha256> verified=1
recipe combat_arms 1
tool chimera_pack <crate version> <commit>
key V1 supplied
kind <path> community                            # only non-original kinds are listed
gen <path> <converter> <version> <params sha256> <input id>[,<input id>...]
need <set> <set>
report <sha256 of the report>
```

Every manifest path is `original` unless a `kind` or `gen` line says
otherwise. Authored content (the logo's characters, arena slices) is
never mixed into a game's manifest. It is its own content id,
`chimera`, built from the repository's own files with the same
pipeline, and its sidecar says `original authored`.

A later manifest format 2 may fold the sidecar in. That needs the
service to serve format 1 to old clients (`GET /m/` by the client's
declared format). Not needed for any phase here.

### 3.9 The report

Written beside the sidecar as `reports/<content>/<build>.toml`, with a
`.txt` summary printed at the end of the run. It holds:

- **Identity**: the original's kind, build, fingerprint, verified or
  not, the keys supplied or absent, and the recipe and tool versions.
- **Discovery**: items per catalogue, with what is new, gone or changed
  since the previous ingest of the same content (by id).
- **Derivation**: per item, the template used, the fields not mapped
  and the defaults used, items without a template (no `class`, not
  dealt), and overlay entries that matched nothing (stale overrides).
- **Sets**: each unit's files, records and plain and stored size, its
  needs, and empty units.
- **Walks**: references to files missing from the original, and files
  only checked for.
- **Converters**: each run or skipped (already stored), with its inputs
  and outputs.
- **Completeness** (with `--check-runs`): files read in no set, and
  files read outside the offered closure.
- **Reproduction**: the manifest content id (3.10) and, when the recipe
  or `assets.lock` names a reference, whether it matches.

The report holds names, sizes and hashes, never file contents or keys.
It may be shared publicly.

### 3.10 Reproducing a pack

A manifest's exact bytes include stored sizes, which depend on the zstd
version and level. The **manifest content id** is the SHA-256 of the
manifest text with the stored sizes left out, plus the sidecar without
its `tool` and `report` lines. The same verified original and the same
recipe and converter versions give the same content id on any machine.

`assets.lock` gains `content = "<64 hex>"` per game. A host who rebuilds
from their own media runs `chimera_pack verify <game> --against <id>` and
knows that their pack is ours. A mismatch report says which sets or
generated records differ.

## 4. Official content updates

Combat Arms' developers ship a patch with two new guns, a map and a
body. The host updates the install and runs `chimera_pack ingest
combat_arms --from <install> --store <server store> --sign`:

1. The new build id is unknown to the recipe. It is ingested with
   `--accept-unknown`, and a one-line recipe change adds the build and
   fingerprint. That is data, not code. Until then the report says
   "unverified".
2. The weapon discoverer finds the new records. Each takes our model:
   derived numbers, a template by `Guntype`, the overlays. A new gun of
   a known `Guntype` gets `class` from its template and joins automatic
   ladders at once, as install weapons do today. A gun of a new
   `Guntype` gets a unit and a generic document without `class`, and
   the report says so.
3. The map's `map/<name>` unit is made, and its fitness is measured by
   `chimera:map_fitness`. Unless `map_pool.toml`'s deny rules match it,
   it is in the pool at its measured weight. Without a measurement it
   would be in at `unknown_weight`, as today.
4. The body's `character/<record>` unit is made from its `MODELBUTES`
   record.
5. The catalogue record is regenerated, so the sandbox lists the new
   guns with their tags and sizes.
6. Records already stored are skipped. The new manifest sits beside the
   old build's, and clients pick the newest build as they do today
   (`served.rs`).

TF2 after phase I6: a new stock item in `items_game.txt` gets a
`weapon/<id>` unit, its numbers from its script (decrypted with the
operator's key) and a template by `item_class`. An unknown
`item_class` gets the safe default.

What can't come without code is new behaviour: a weapon mechanic no hook
implements, a new file format, a new map entity. The report makes those
visible: it lists the unmapped fields and unknown types.

## 5. Custom content

### 5.1 Namespaces

- **Official content ids** are the registered games' ids (`GameInfo::id`:
  `cs_source`, `combat_arms`, `hl2dm`, `tf2`, `halo_ce`) and `chimera`.
  They never contain a dot.
- **A custom namespace** is `<author>.<pack>` (`alice.goldguns`). It
  always contains a dot, so it can never equal a game id or a console
  namespace.
- Item ids follow the existing form: `alice.goldguns:golden_m4`,
  `alice.maps:arena1`. Set names are the same as official ones
  (`weapon/golden_m4`, `map/arena1`) within the pack's manifest
  (`manifests/alice.goldguns/<version>.txt`).
- A pack **extends** one game (`extends = "combat_arms"`). Its weapons
  use that game's movement, HUD, hooks and formats, and its ids show
  "custom" wherever names are shown ("Golden M4 (custom)"). A pack with
  maps or bodies only may extend several games or none (Chimera's own
  formats).
- Who may use a namespace is open question 4.

### 5.2 The pack format

The author's source folder:

```
goldguns/
  pack.toml             namespace, version, extends, title, licence, author's public key
  weapons/*.toml        weapon documents (docs/weapon-data.md); `base` may name an official weapon
  characters/*.toml     bodies: model, skins, hit boxes, movement figure (from the game's model)
  maps/                 map files in a supported format, with pool data
  hud/                  HUD content data and pictures (5.7)
  files/                models, textures and sounds the documents name
  overrides/            display names and tags for its own items only
```

A weapon document is our ordinary format. `base =
"combat_arms:m4a1"` makes a golden M4 a few lines: new skins and
numbers, with the official M4's hooks and animations inherited through
the `known` sets that `WeaponSet::parse` already takes.

**Mounting**: a pack is its own content with its own mount layer, read
as `alice.goldguns`. A path its documents name resolves in the pack
first, then in the extended game's mount. The pack is never a layer in
front of the official game, so a pack can't replace an official file
for any other content.

### 5.3 Building, signing and trust

`chimera_pack ingest custom --from goldguns/ --store <dir> --author-key
<file>` runs the same pipeline. Here the original is the author's
folder, identified by its own hash, and the recipe is the pack's
`pack.toml` with the generic custom recipe. It:

1. Validates (5.4) and refuses with a report on any violation.
2. Derives units the same way (walkers of the extended game's formats).
   `needs` names the official units the pack uses
   (`combat_arms:weapon/m4a1` for a reskin).
3. Runs the same converters (the catalogue, fitness for maps).
4. Signs twice:
   - the **author's signature**, made with the author's Ed25519 key
     over the manifest and sidecar (`<version>.author.sig`). It says who
     made the pack and that it is unchanged;
   - the **service's signature**, as for any manifest, when a service
     publishes it. It says that this service serves the pack.

Trust works in three places:

- **The service** publishes only packs its operator accepts (a
  `chimera_pack publish-custom` step that checks the author signature
  and the report).
- **The game server** offers only packs on its allow list:
  `[custom] packs = ["alice.goldguns@<content id>"]` in its config, or
  a `chimera:custom_packs` cvar. Each is pinned by content id and
  author key.
- **The client** checks both signatures. The service's is checked as
  today. The author's is checked against the key the offer names. The
  join screen says that the match uses custom content and whose. A
  client setting refuses custom content (open question 5).

Revoking an author's key can come later through the hub's revocation
feed.

### 5.4 What custom content may and may not contain

May:

- data documents in our formats, each validated by its parser
  (`WeaponSet::parse` against the extended game's sets);
- models, textures, sounds and maps in formats our loaders read, either
  the extended game's own formats or Chimera's (open question 7);
- overlays of its own items' names and tags.

May not:

- **any code**: no scripts, binaries, shader source, Lua or WASM, and no
  new hook implementations. A document may name only hooks that the
  extended game or Chimera registers. The report lists the hooks named,
  and an unknown one is refused. A map's entity logic is allowed only
  through the entities our engine implements, which is data, as
  community maps' logic already is;
- files outside its namespace, or anything that overrides official
  content;
- URLs or anything else a client would fetch from elsewhere;
- **original game files.** The pipeline refuses a pack any of whose
  records has the same id as a record in an official manifest of the
  operator's store. That catches byte-identical copies. Anything
  derived from originals is the author's responsibility, stated in
  `pack.toml`'s licence line.

Limits: file types are checked against the loaders' own lists. Every
file is parsed at build time, with size and count caps per unit and per
pack. Clients parse again with the same caps, so decompression bombs and
huge counts are refused.

### 5.5 Delivery: the no-fetch-in-match rule holds

A server playing with a pack names its units in the `AssetOffer` as it
names official ones: content id, units, manifest content id and author
key (a `NET_VERSION` bump). The client fetches them with the join's or
level change's download, or with the next map ahead. Nothing is fetched
during a match.

A ladder's drawn custom guns are known at the match's start, as official
ones are (`AssetHooks`). A dedicated server with no copy fetches the pack
from its service with its own credential, as it does for games
(playtest-hosting.md, "The server's own game files").

### 5.6 Custom content in ladders and minigames

- A pack's weapons enter the `WeaponCatalog` at run time, parsed with
  the extended game's sets as `known`. Those with a `class` join
  automatic ladders through the existing rule ("every weapon of its own
  in the catalogue whose data names a `class`", game_parts.rs).
- `GameParts` is `&'static` Rust today. A pack registers a data parts
  entry (3.4) into `PartsRegistry` at run time, with its movement and
  HUD those of the game it extends.
- Minigame definitions opt in by data. An automatic ladder takes
  `custom = ["alice.goldguns"]` or the server's allow list. A
  hand-written ladder names `alice.goldguns:golden_m4` directly.
- The ladder draw (backlog "Ladder draw") deals games equally. A pack's
  guns count within the share of the game they extend by default, so a
  50-gun pack doesn't crowd the others out (open question 6).
- A pack's maps join a pool through its own pool data and measured
  fitness. Its map ids are `alice.maps:arena1`.

### 5.7 Maps, player models and HUD content

The same shape applies to each:

- **Maps**: a map unit with its files, fitness measured at build, and
  pool rules as data. A map in a game's format extends that game
  (custom-maps.md's packages, as designed there). Community maps already
  in CS:S's download folder are open question 3.
- **Player models**: a `character/<id>` unit. Its document names the
  model, skins, hit boxes and movement figure, and a skeleton the
  extended game's animations can drive. Bodies in our own rig (backlog,
  "Our own default assets") use Chimera's format.
- **HUD content** (later): data for the HUD elements a game registers
  (layouts, pictures, fonts, colours, kill-feed icons), never new
  elements, which would be code. A HUD pack extends one game's HUD.

### 5.8 The legal side

Official content reaches a store only from the operator's own media,
through the pipeline. The repository holds recipes, converters and
reference ids, never files or keys. Custom packs are their authors' own
work, with the originals check of 5.4. Neither kind is committed to the
repository. A test pack for the pipeline's own tests is generated by
the tests from synthetic bytes.

## 6. How it fits with the rest

- **Atomic per-unit downloads**: a unit is a set plus its needs. "Ready"
  means every record of the closure is in the store. A per-gun unit is
  `weapon/<id>` (with `parts/<id>`), a TF2 class `players/<class>` (the
  Spy needing every class), and a Halo character the converter's
  generated unit.
- **`request_set(game, set)` and `SetProgress`**: they fetch the closure.
  `Absent{size}` comes from the catalogue record's sizes or the
  manifest's `set_size`, with no fetch.
- **Service-first**: unchanged (`served.rs`). An ingested store is
  served alone, and an install still layers over it only at the same
  build.
- **Server credentials**: unchanged. A server's own fetch covers custom
  packs too.
- **Sandbox tags and filters**: tags are derived by one function from
  the final documents and shipped in the catalogue record (3.4, 3.6).
- **Ladder draw**: discovery only grows the guns a game offers. The
  draw's equal share per game keeps a game with 2,000 discovered guns
  from swamping the others, and custom guns share their game's turn.
- **Hub accounts**: a custom namespace could be bound to an account
  (hub.md, section 5) instead of a bare key (open question 4).

## 7. Migration from today's recorded sets

Today's server store mixes four sources: whole publishes (CS:S, Combat
Arms, HL2:DM, Halo), loader-traced `sets`, sets from run logs (TF2's
`base` and `map/ctf_2fort`, older map sets, and `lean`'s split), and sets
copied by `--sets-from`.

1. **Ingest beside it**: run the pipeline into a hard-linked copy of the
   server store, so records are shared and only manifests are new (as
   the hosting doc's `lean` step does).
2. **Diff**: per set name, list the files added and removed against
   today's manifests. Feed the rehearsals' and playtests' run logs and
   the access log's ` on-demand` lines to `--check-runs`. Fix
   declarations until nothing that was read is missing. Every removal
   must be explained (a file only checked for, a run's own leftovers).
3. **Swap**: back up the manifests (playtest-hosting.md's snapshot
   step), move the new manifests and sidecars in, and sign. Set names
   are unchanged and format 1 is unchanged, so shipped clients notice
   nothing but new manifest ids. Update `assets.lock` with the ids and
   the content ids.
4. **TF2**: `scope = "declared"` packs exactly what its units and shared
   sets name from the install (with the key), replacing the two
   recording runs.
5. **Retire**: `pack --from`, `publish --sets-from`, `lean` and the run
   recordings in the hosting doc. `pack`, `sets` and `publish` stay one
   release as wrappers, then go. playtest-hosting.md's "Publishing the
   game files" becomes one `ingest` line per game.

## 8a. The user's answers (2026-11-16)

- **1, the command:** a `chimera_pack ingest` subcommand. Releases (user, 2026-11-17): not yet. Host tools aren't shipped today, so others build from source.
- **2, whole or declared packs:** keep the four games whole for now (the recommendation).
- **3, community maps:** neither a `community` kind nor a separate pack. Community maps are a hierarchy under the game: `cs_source` holds the base game's content, and under it, individual community maps as units of their own, attributed (author, source), e.g. `cs_source/map/community/gg_mario_vs_wario`. They can be added piecemeal over time; there are more gun-game maps to add.
- **4, namespaces:** user-made content is kept in USER namespaces, separate from the games' namespaces. A user's asset may be based on a game (e.g. a skin for a CS:S gun) or on Chimera itself, which is treated like a game namespace (like a game crate) for our own and users' original content. Some attribution or mapping links a user asset to what it's based on. **On hold:** whether hub accounts can publish their own content; don't design publishing by accounts yet.
- **5:** ask the first time per server before accepting its custom packs.
- **6:** custom guns share the turn of the game they extend. A fully separate user creation (based on Chimera) is its own entry.
- **7, formats:** both (user, 2026-11-17): custom packs may use the base game's native formats and Chimera's own (glTF, PNG, OGG).
- **8, reskins:** yes, and the user prefers a **variant system** over copying. A gun can have variants under it in the graph; a variant replaces any subset of the gun's parts (only the texture for a skin, or the texture and sounds, and so on) and depends on the gun's unit for the rest. A skin is just a variant that changes textures. It fits the asset graph's `variant-of` edge (3.5a).
- **9:** `assets.lock` is the repo file that pins which build of each game's manifest the code expects (docs/assets-for-developers.md). Publishing the content ids there means anyone rebuilding from their own media can check their result matches. The user didn't object; treat it as yes.
- **10:** yes, Combat Arms' keys may come from environment variables.
- **11:** Halo character units in our own format.
- **12:** converted maps on the service only if measurement shows it's worth it. Fine.
- **Cross-game balance as a host option:** ON by default.
